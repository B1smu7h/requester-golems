# Requester Golems V1.1 — Technical Design (Pass 2)
## Golem Identity & Assignment

**Status:** Research-backed technical design; implementation not started  
**Repository baseline:** `main` @ `e46a25acc512a412e003fdd8cd4b156352319a12`  
**Target:** Minecraft Java Edition 26.3 · Fabric Loader 0.19.5 · Fabric API 0.161.0+26.3 · Java 25  
**Mod baseline:** 1.0.0

Evidence labels: **CONFIRMED** = checked in current repository or current-version references; **DESIGN** = approved product intent; **PROVISIONAL** = recommended architecture needing prototype validation; **OPEN** = decision/research still required.

## 1. Executive summary

V1.1 should add a persistent identity and owner to Requester Golems, an individual golem configuration screen, and exclusive chest eligibility without replacing V1 transport. The conversion item changes from a diamond to one redstone block for both golem and chest conversion.

The most important architecture issue found in research is that **a chest-only list of assigned golems is insufficient** to represent the agreed default-global behavior. If a golem has zero exclusive assignments it is global; if it is assigned to A and B it must not service C. That distinction needs to be discoverable from the golem's authoritative assignment state, or from a consistent server-side index. A central logistics system is not needed, but a small persistent identity directory may be needed for global name/ID lookup.

Recommended direction:
- Keep the vanilla Copper Golem entity and existing mixin/access-interface approach.
- Add mod-owned persistent fields to Requester Golems: owner UUID, editable display name, stable public ID, and exclusive requester-chest references.
- Use the vanilla entity UUID as the internal entity key; do not invent a second internal UUID without a concrete need.
- Add a server-side persistent directory/index only if required to support name/ID search for golems outside loaded chunks. This is an identity lookup service, not a logistics network.
- Filter chest/job eligibility before a golem claims a job. Do not add priority scheduling.
- During active transport, let the currently claimed job reach a safe terminal state (deliver if still valid, otherwise use the existing physical cargo-return/recovery path); do not simply stop the behavior or teleport cargo. Exact behavior must be confirmed by focused prototype tests.
- Preserve legacy V1 chest behavior: no assignment metadata means global eligibility.

### 2.2 Existing persistence pattern — CONFIRMED
The mod already stores custom entity state through injected `addAdditionalSaveData` and `readAdditionalSaveData` methods using namespaced `ValueOutput`/`ValueInput` keys. The chest mixin uses the equivalent block-entity save/load hooks. V1.1 can extend these established patterns, but must avoid key collisions and preserve existing recovery fields.

### 2.3 Existing UI/network pattern — CONFIRMED
The chest menu is a `ChestMenu` subclass. Custom request edits use registered Fabric custom payloads. The server receiver checks that the player's current menu is a RequesterChestMenu and validates the request index/stack bounds. New assignment payloads should follow this pattern and add stronger ownership, target, and distance/world validation appropriate to entity assignments.

### 2.4 Existing transport boundary — CONFIRMED
`RequesterTransportBehavior` discovers requester chests around a golem, chooses the nearest chest with active requests, then calls `requestergolems$claimJob()`. The chest currently marks a claimed job IN_PROGRESS. The behavior stores current requester/source positions and cargo/recovery state. Eligibility should be checked before the claim boundary so ineligible golems do not reserve work.

Caution: current source discovery iterates a local BlockPos volume and current job state is owned by the requester chest. Do not rewrite that system as part of identity/assignment.

## 3. Minecraft 26.3 entity findings

### 3.1 Native ownership — CONFIRMED with source-reference caveat
The current 26.3 CopperGolem API hierarchy is `CopperGolem extends AbstractGolem`; AbstractGolem extends PathfinderMob. It does **not** extend `TamableAnimal`. The published 26.3 API class hierarchy lists Copper Golem's direct superclass and does not show the `OwnableEntity` interface that TamableAnimal implements. Therefore the dog/wolf taming-owner model should not be assumed reusable. Add a mod-owned owner UUID unless direct inspection of the exact Mojang-mapped runtime source proves an alternative suitable owner API.

Source references:
- https://aldak.netlify.app/javadoc/26.3.x/net/minecraft/world/entity/animal/golem/coppergolem
- https://aldak.netlify.app/javadoc/26.3.x/net/minecraft/world/entity/animal/golem/abstractgolem
- https://aldak.netlify.app/javadoc/26.3.x/net/minecraft/world/entity/tamableanimal

### 3.2 Entity identity — CONFIRMED general API; public ID design PROVISIONAL
Minecraft entities already have a persistent entity UUID. Use this UUID for internal identity and assignment references. The network entity ID is not a durable reference and must not be stored as the assignment key.

A user-friendly discriminator like `Name#0000` is a separate presentation/search requirement. A truncated UUID is simple but not mathematically collision-free; a random four-digit suffix requires collision checking and persistence. Recommended prototype: persist a public ID once at conversion, ensure uniqueness through a small server-level saved registry, and never regenerate it on rename/reload. Decide the final length after usability review. Do not derive the public ID anew every time the UI opens.

### 3.3 Interaction and UI opening — PROVISIONAL
The current mod already injects into CopperGolem.mobInteract for conversion. The 26.3 Copper Golem exposes mobInteract, but the exact interaction result/priority and the effect of returning SUCCESS must be tested against vanilla name-tag and item interactions. Add a separate condition for requester golems with empty hand and no carried item; preserve existing conversion behavior for unconverted golems. Prefer a narrowly scoped injection at the existing interaction boundary over replacing the entire interaction method.

The empty-hand/not-carrying requirement is product intent. Confirm which hand state should be checked and how the interaction is handled on client vs server before implementing.

## 4. Recommended state model

### 4.1 Requester Golem — PROVISIONAL
Extend `RequesterGolemAccess` with accessors for:
- owner player UUID (nullable only for legacy migration state);
- editable display name;
- stable public ID;
- exclusive assignment set;
- optional identity initialization/version marker.

Persist these through the existing entity save/load hooks. Use UUIDs, not player usernames, because usernames can change. Owner checks compare the acting player's UUID.

The vanilla entity UUID remains the canonical internal golem key. The public ID is for humans and lookup only.

### 4.2 Requester Chest reference — OPEN / RESEARCH
A chest needs a stable identifier for assignment references. Vanilla block entities do not automatically provide the same universal persistent identity contract as entity UUIDs. Options:
1. persist a mod-generated requester-chest UUID when it is converted;
2. use dimension + BlockPos as the chest reference, with explicit stale-reference cleanup.

Recommendation: use dimension + BlockPos for the first implementation if requester chests cannot move and the assignment set lives on the golem; validate chunk/world references without force-loading. If cross-dimension or block replacement semantics make this brittle, use a persistent chest UUID. Do not decide without testing chunk unload, block break, and chest reconversion.

### 4.3 Where assignments live — PROVISIONAL recommendation
The authoritative exclusive-assignment set should be readable from the golem, because “zero exclusive assignments = global” is a golem property. The chest UI can manage that set, but the chest should not be the only source of truth unless a server-side reverse index is also maintained. A chest-only list cannot by itself tell a golem whether it has been assigned elsewhere.

If the implementation needs the chest screen to show every assignment and allow lookup by public ID/name even when a golem is unloaded, add a small persistent directory/index mapping public ID → entity UUID, owner UUID, display name, and enough location metadata to report whether the entity is currently loaded. This directory must not schedule jobs, load chunks, or become a logistics network.

### 4.4 Global and exclusive semantics — DESIGN
- Empty exclusive-assignment set: global eligibility, retaining V1 behavior.
- Non-empty set: eligible only for listed requester chests.
- Removing the final assignment restores global eligibility.
- A golem can be assigned to multiple chests; a chest can be served by multiple golems.
- Assignment changes are eligibility changes, not priority/scheduling changes.

## 5. Eligibility and transport transition

### 5.1 Claim boundary — PROVISIONAL
Add an eligibility predicate immediately before a requester chest's job is claimed. For each candidate chest:
1. verify it is a requester chest with active requests;
2. check the golem's assignment set against that chest reference;
3. skip ineligible chests;
4. retain existing nearest-eligible-chest selection and existing job claiming behavior.

Important: do not claim a job and then discover the golem is ineligible; that risks a stranded IN_PROGRESS job. Avoid changing request ordering or adding a new priority queue.

### 5.2 Reassignment while busy — OPEN decision; recommended safe rule
Current behavior has explicit cancellation and return-to-source phases and persists cargo/recovery metadata. Stopping a behavior while carrying invokes emergency rollback behavior, so assignment changes must not be implemented as a blind behavior reset.

Recommended rule for the first implementation:
- Assignment changes affect **future claims immediately**.
- A golem that already claimed a job may finish that job if its requester chest and request are still valid, then must obey the new assignment set for its next claim.
- If the request/chest becomes invalid or the job is cancelled, use the existing physical return/recovery flow.
- Do not interrupt a carried delivery solely because the assignment set changed.

This is a recommendation to validate in a prototype, not a confirmed current behavior. Test during approach to source, while opening/picking up, carrying, approaching destination, during delivery, and after save/reload.

## 6. Assignment UI and server security

### 6.1 UI — DESIGN + OPEN
Requester Golem UI: name, public ID, and an inert/clearly marked future upgrade-slot area if that placeholder does not complicate this release. Requester Chest UI: add/remove by name or public ID, list current assignments, show owner/availability feedback, and optionally show nearby eligible golems.

Nearby selection is convenience-only. Name/ID search is the required method and is not inherently limited by distance.

### 6.2 Serverbound payload validation — REQUIRED
Every add/remove request must be validated on the logical server:
- sender has the expected requester-chest menu open;
- target chest still exists, is still a requester chest, and matches the menu's chest reference;
- target golem ID resolves to a Requester Golem, not an ordinary Copper Golem;
- the acting player UUID matches the golem owner UUID;
- request is well-formed and references valid dimensions/positions/IDs;
- no arbitrary client-supplied entity network ID is trusted as a persistent identity;
- operation is idempotent and safe if repeated;
- no packet triggers chunk force-loading.

Fabric's networking docs explicitly state that payloads must be validated server-side. Current project payloads already check menu and basic bounds; V1.1 should extend validation for authorization and target validity.
Reference: https://docs.fabricmc.net/develop/networking

## 7. Persistence, unloaded entities, and migration

### 7.1 Legacy chest default — DESIGN
If assignment fields are absent on a V1 requester chest, it must retain global behavior. Absence/empty data must not accidentally mean “no golems allowed.”

### 7.2 Legacy golem owner — OPEN product migration
Existing V1 requester golems have no recorded converter UUID. It is not safe to infer an owner from current proximity or the player who first opens the UI. Options needing product choice:
- legacy golems become unowned and can be claimed by the first player who explicitly claims them;
- legacy golems are assigned to the server/ownerless state and cannot be exclusively assigned until claimed;
- a one-time migration prompt lets an authorized player claim nearby/selected legacy golems.

Recommended simplest behavior: mark old requester golems as legacy-unowned; show a clear claim action to the player interacting with the golem, and record that player UUID only after explicit server-side confirmation. Do not silently assign ownership to whoever happens to load the chunk.

### 7.3 Unloaded or destroyed targets — REQUIRED
Do not force-load chunks to find or modify a golem. Persist stable references; treat unloaded entities as offline, not invalid. When a requester chest is broken, stale assignment references must be harmless and eventually cleaned. Decide whether break events eagerly remove that chest from loaded golems or whether stale references are lazily pruned on load/eligibility checks.

### 7.4 Persistent directory — PROVISIONAL
Global search by name/public ID when the entity is far away or unloaded cannot rely solely on scanning loaded entities. Investigate Minecraft 26.3 SavedData/level attachment options and their Fabric compatibility. Fabric's Data Attachment API documents persistent attachments for entities, block entities, levels and chunks; however, this project may not need a new dependency or a world-level attachment if the public ID is directly resolved through a smaller index. Validate the API in the exact current environment before selecting it.
Reference: https://docs.fabricmc.net/develop/serialization/data-attachments

## 8. Conversion cost change

The current golem conversion in `CopperGolemMixin` checks for `Items.DIAMOND`, sets requester mode, consumes one item on the server, and applies the custom name. The chest conversion path must be inspected in `ChestBlockMixin` before patching. Change both paths to require exactly one redstone block in place of the diamond.

Acceptance:
- one redstone block converts the golem/chest and is consumed once in survival;
- diamonds no longer convert either target;
- wrong/insufficient item does not mutate requester state or consume an item;
- creative-mode consumption follows the intended vanilla convention;
- client/server interaction does not double-consume.

## 9. Initial acceptance test matrix

1. V1 baseline builds before code changes.
2. Convert a golem and verify owner UUID, display name, public ID, and requester flag persist after save/reload.
3. Rename and verify internal UUID/public ID remain stable.
4. Verify different golems cannot share a public ID.
5. Existing V1 requester golems load with the documented legacy-unowned behavior and retain transport recovery state.
6. Empty assignment set keeps global V1 eligibility.
7. Assign to A and B; golem can claim A/B jobs but never C.
8. Remove A; golem can still service B but not C.
9. Remove final assignment; global behavior resumes.
10. Multiple golems assigned to one chest can service jobs without duplicate claims.
11. An ineligible golem never claims a job.
12. Owner can add/remove assignments; another player cannot, including via forged payload.
13. Name/ID lookup works for loaded targets; unloaded-target behavior matches the documented index/availability rule without force-loading.
14. Assignment changes during each transport phase do not lose/duplicate cargo or strand jobs.
15. Broken requester chest and stale assignment references do not crash or load chunks.
16. Both conversion paths require one redstone block, not a diamond.
17. Ordinary Copper Golems and all V1 request/job/recovery behavior remain unaffected.
