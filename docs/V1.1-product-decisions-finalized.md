# Requester Golems V1.1 — Finalized Product Decisions

**Status:** Product decisions agreed; technical validation and implementation still pending  
**Target:** Minecraft Java Edition 26.3 · Fabric Loader 0.19.5 · Fabric API 0.161.0+26.3 · Java 25  
**Related technical research:** [Pass 2 — Identity & Assignment](V1.1-identity-and-assignment-technical-design-pass-2.md)

This document records the decisions made during the V1.1 design conversation. These decisions define intended player-facing behavior; they do not replace implementation research or acceptance testing.

## 1. Identity

- Every Requester Golem uses its existing Minecraft entity UUID as its stable internal identity.
- The player-facing public ID is a separate, short, human-readable identifier. The exact format and length remain an implementation detail to choose after uniqueness and usability are evaluated.
- The public ID never changes after initialization, including when the golem is renamed.
- The display name is editable and does not need to be unique. The ID distinguishes golems with identical names.
- A public ID must be generated/persisted safely and checked for collisions. Do not derive a potentially colliding shortened ID anew each time the UI opens.

## 2. Ownership and legacy migration

- The player who converts a Copper Golem into a Requester Golem becomes its owner.
- Existing V1 Requester Golems have no recorded owner and start unowned after upgrading.
- The golem's UI displays a claim button only while the golem is unowned.
- Claiming is an explicit player action. The first valid server-side claim succeeds; concurrent or later claims must fail safely.
- An owned golem cannot be claimed or taken over by another player through ordinary interaction.
- Owner checks use the player's UUID, not username.
- Everyone may inspect a golem's public identity. Only its owner may rename/configure it or manage its assignments.

## 3. Search and loaded entities

- Assignment search targets currently loaded Requester Golems only.
- Unloaded golems do not appear in the selector until they load naturally.
- Do not force-load chunks to search for, inspect, assign, or configure golems.
- Identity and assignments must still persist through normal save, unload, reload, and world restart.

This intentionally favors the simpler implementation over a persistent directory for unloaded golems in V1.1.

## 4. Requester chest identity

- An assignment references a requester chest by **dimension + block coordinates**.
- Before implementation, validate that breaking a requester chest invalidates its old assignments and that a newly converted requester chest at the same coordinates does not inherit stale assignments or jobs.
- Stale references must never cause crashes or chunk loading. If the coordinate-based design cannot safely meet these rules, pause and revisit the reference model before proceeding.

## 5. Assignment semantics

- A Requester Golem with no exclusive assignments remains globally eligible for requester chests, preserving V1 behavior.
- Once it has one or more exclusive assignments, it may start jobs only at those assigned requester chests.
- Removing its final assignment restores global eligibility; no separate “global” toggle is needed.
- One golem can be assigned to multiple requester chests, and one requester chest can have multiple assigned golems.
- Assignment determines job eligibility, not priority or scheduling. Existing V1 job-selection behavior chooses among eligible jobs.
- Only Requester Golems participate in assignments. Ordinary Copper Golems remain unaffected.

## 6. Changes while a golem is busy

Assignment changes take effect immediately for **future job claims**, but must not interrupt safe handling of cargo already in transit.

- If the golem has already claimed a job and the requester chest/request remain valid, it may finish that job even if its assignment has since changed.
- The updated assignment set applies to the next job claim.
- If the request is cancelled or the chest/job becomes invalid, use existing physical return and recovery behavior.
- Never delete, duplicate, teleport, or abandon carried cargo.
- Validate this rule during each transport phase, including save/reload. If current implementation behavior contradicts this design, adapt the transition safely rather than resetting the transport behavior blindly.

## 7. UI and naming

- The individual Requester Golem UI shows its editable name and stable public ID.
- The golem UI may reserve a clearly marked area for future upgrade slots, but V1.1 does not implement upgrades.
- The requester chest UI is where owners search for golems and add/remove assignments.
- Name/ID search is required. Nearby-go​lem selection is optional convenience, not a requirement.
- Names should have a reasonable length limit and reject control/formatting input that could break the UI. Exact limit and permitted character set can be finalized during UI implementation.
- Unowned golems show the claim button; owned golems do not.

## 8. Conversion item

Replace the diamond cost with **one redstone block** for both:
- Copper Golem → Requester Golem
- Copper Chest → Requester Chest

The server must consume exactly one redstone block in survival, never double-consume, and not convert when the player lacks the correct item. Diamonds must no longer perform either conversion. Creative behavior should follow the established vanilla convention and be tested.

## 9. Engineering constraints and acceptance gates

- Preserve V1 request, transport, cancellation, rollback, death, and recovery invariants.
- Check assignment eligibility before claiming a job; an ineligible golem must never reserve work.
- Validate ownership, target validity, requester type, menu/chest identity, and relevant world/distance constraints on the logical server for every mutating payload.
- Do not trust client-provided transient network entity IDs as persistent identity.
- Do not add a logistics network, priority scheduler, chunk force-loading, or a global unloaded-golem directory in V1.1.
- Ordinary Copper Golems must not gain requester-only behavior as a side effect.
- Build and test against the exact project baseline before and after each small implementation step.

3. Implement identity/owner persistence and explicit legacy claiming.
4. Add the minimal individual golem UI and safe name editing.
5. Add assignment storage, chest UI, and validated serverbound operations.
6. Apply eligibility filtering before job claim and test reassignment during transport.

8. Run the acceptance matrix from the Pass 2 technical design, adding tests for every decision above.

**No Java code or runtime behavior is changed by this decision record.**
