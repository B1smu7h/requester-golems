## 3. Findings that materially affect implementation

### 3.1 Individual golem screen: do not turn the golem into a new entity class

The current mod augments the vanilla Copper Golem through mixins. Keep that approach. Add a new menu type and a client screen for the individual Requester Golem; do not replace the vanilla entity or duplicate its AI.

Minecraft 26.3 references expose `CopperGolem.mobInteract(Player, InteractionHand)`, and the 26.3 `ServerPlayer` API exposes server-side `openMenu(MenuProvider)`. The general menu pattern is to open on the logical server and use a registered menu type plus a client screen. The exact mapped signatures still need to be compile-verified in this project's Fabric Loom dependencies.

The golem is not a `TamableAnimal`; owner identity remains mod-owned UUID state.

### 3.2 The screen must identify the target by stable UUID, not entity network ID

Network entity IDs are transient and should not be persisted as identity. For the first interaction, the server already has the actual golem instance. The menu can retain a server-side entity UUID reference; the client needs only the fields required to render the screen and issue edits. Any mutation packet must be resolved and validated on the server and must not trust a client-supplied network entity ID as permanent identity.

Because the design explicitly searches loaded golems only, server lookup can scan currently loaded entities in the server's loaded levels. Do not use APIs that request a chunk load just to resolve an assignment target.

### 3.3 Public ID: sequential world-wide allocator (decision confirmed)

The user confirms the original intended direction: public IDs are sequential, human-friendly labels, for example `Requester Golem #000042`. The entity's Minecraft UUID remains the immutable internal identity; the sequential number is a separate public identifier.

Use a small persistent world-level counter (or equivalent persistent server/world state supported by the exact 26.3 APIs) that allocates the next number atomically on the server. Persist the next counter value so it survives save/reload and server restart. Never reuse an issued number, including after a golem dies or is removed. Formatting width is presentation only: numbers may grow beyond the minimum padded width without truncation.

This is a counter, **not** a global golem directory: no list of unloaded entities is maintained, no chunk is force-loaded, and assignments still resolve only against currently loaded golems. The counter avoids collision-prone truncated UUIDs while keeping the player-facing ID short.

Legacy golems missing the public-ID field receive an ID through the same allocator when first migrated/initialized. This initialization must not claim ownership; legacy ownership remains explicitly unowned until a player deliberately claims the golem. Ensure initialization is idempotent so an entity does not receive a fresh number on every load.

### 3.4 Assignments should live on the golem

The current requester chest owns its jobs and request data; the golem owns its physical cargo/recovery state. The assignment set is a golem eligibility rule, so store it on the golem alongside owner/name/public ID and persist it through the existing entity save/load hooks.

Represent each assignment as a dimension key plus immutable BlockPos. Empty set means global eligibility. Non-empty set means exclusive eligibility only at those positions. This avoids a reverse directory and naturally supports multiple chests per golem and multiple golems per chest.

### 3.5 Chest UI can enumerate currently loaded golems without an index

When the requester chest screen opens or refreshes, the server can enumerate loaded Requester Golems and present those matching the search text or existing assignments. Keep the candidate list server-authoritative; client text is only a search query. If a golem unloads after appearing, an assignment mutation must re-resolve it and fail safely rather than loading its chunk.

The selector should show name and public ID together to disambiguate duplicate names. Search should match either. Nearby selection is optional and can be omitted if it complicates V1.1.

### 3.6 Serverbound changes need complete validation

For claim, rename, assignment add, and assignment remove operations:
- execute mutations on the logical server;
- validate the player is using the expected screen/menu and that the referenced target is currently loaded;
- validate target is still a Requester Golem or Requester Chest as applicable;
- validate ownership against player UUID for all owner-only mutations;
- validate name length/characters and assignment dimensions/coordinates;
- validate that a referenced chest still exists, is a requester chest, and is the intended chest;
- keep operations idempotent;
- reject malformed or stale requests without loading chunks.

Fabric's published networking guidance is for 26.2 rather than 26.3, but the project already uses the current custom payload registration/receiver pattern. Use the actual 26.3 compile-time API as source of truth. Reference: https://docs.fabricmc.net/develop/networking

### 3.7 Current chest screen is tightly coupled to a 176px layout

The existing screen uses hand-rendered backgrounds, off-screen backing slots, data slots, and explicit mouse handling. Adding assignment controls directly into the existing settings list risks reproducing the prior interaction/rendering bugs.

**Recommendation:** add a dedicated assignment view/state in the chest screen and keep it isolated from request-slot and cancellation mouse paths. Avoid changing the existing request view or active-request cancellation implementation. If the assignment view needs a larger screen, change its dimensions deliberately and test at multiple GUI scales; do not resize the whole menu's slot coordinates as a side effect.

### 3.8 Conversion cost change is localized but server/client behavior must be checked

The current golem conversion intercepts `mobInteract` and consumes a diamond server-side; the copper chest conversion intercepts `useItemOn`, only converts SINGLE copper chests, and consumes a diamond server-side. Both item checks should change to `Items.REDSTONE_BLOCK`.

Preserve the current server-only mutation pattern. Acceptance tests must confirm that survival consumes exactly one redstone block, creative mode follows vanilla item-consumption convention, client/server interaction doesn't double-consume, diamonds no longer convert either target, and double copper chests remain ineligible for conversion.

## 4. Proposed implementation shape

### Golem state (entity-persisted)
- owner player UUID, absent for legacy-unowned golems;
- editable display name (sensible default on conversion);
- stable public ID initialized once and persisted;
- exclusive assignment collection of dimension + BlockPos;
- existing requester, rollback, and recovery fields untouched.

### Golem interaction and screen
- Existing unconverted golems retain the conversion interaction.
- Converted Requester Golems open their UI only on empty-hand interaction and only when not carrying cargo.
- The UI displays name and public ID, provides owner-only rename/configuration, and shows a claim button only for unowned legacy golems.
- The server checks ownership and unowned state again when a claim/rename request arrives.
- Claim race is resolved atomically on the server; first successful claim wins.
- Upgrade slots may be visually reserved only if they do not introduce unnecessary menu complexity; no upgrades are implemented in V1.1.

### Assignment view
- Search by display name or public ID.
- List currently loaded Requester Golems, including current assignment status and owner/availability where useful.
- Only the owner of each golem can add/remove that golem's assignment. Other players can inspect public identity but cannot alter it.
- The chest UI identifies the target chest by dimension + BlockPos.
- Empty assignment set stays global. Adding first assignment makes the golem exclusive; removing last assignment restores global behavior.
- Chest breaking/reconversion must not resurrect stale assignments. Because assignments live on golems, validate chest identity against current block entity requester state; stale coordinates are inert and can be lazily pruned when encountered.

### Transport eligibility
- Modify candidate discovery so the assignment predicate is checked before a chest's `requestergolems$claimJob()` call.
- Preserve existing nearest eligible requester-chest behavior, job ordering, source search, and cooldown behavior.
- Do not interrupt a valid claimed job solely because assignments changed.
- If job/request/chest becomes invalid or cancelled, use the existing physical return/recovery path. Never reset transport blindly while carrying.
- An ineligible golem must not claim/reserve work.

### Conversion
- Replace diamond with redstone block for both conversions; do not otherwise refactor the interaction hooks.

## 5. Focused risks and validation

1. **Build/API risk:** the exact `MenuProvider`, `MenuType`, screen, `Component`, `ValueInput`/`ValueOutput`, and interaction signatures must compile against the exact project dependencies. Public Javadocs support the pattern but do not replace compilation.
2. **UI regression risk:** existing custom chest settings screen is sensitive to slot position, mouse interception, and GUI dimensions.
3. **Cargo invariant risk:** assignment changes must not stop the active transport behavior while a golem holds an item.
4. **Chest replacement risk:** dimension + BlockPos alone is not a generation ID. The current requester flag must be checked, and stale assignments must not be mistaken for a newly converted chest at the same location. If safe disambiguation cannot be established with block break/reconvert lifecycle, revisit the chest reference before coding.
5. **Public ID allocation:** sequential IDs require persistent world/server counter state. Counter increments and entity initialization must be server-only, durable, and idempotent; never reuse allocated numbers.
6. **Legacy migration risk:** missing owner/name/public-ID fields must initialize to unowned and preserve existing recovery state. Claiming must never occur automatically.
7. **Permissions risk:** opening/inspecting is public; mutations are owner-only. Validate all mutations server-side.

## 6. Suggested one-sweep implementation order

This is a dependency order, not a requirement to release partial features separately:

1. Build the untouched V1.0 code against the current environment; confirm branch HEAD.
2. Add entity-persisted identity, owner, display name, and assignments without changing behavior.
3. Add stable public-ID encoding and explicit claim handling.
4. Add and register the individual golem menu/screen and rename/claim payloads.
5. Add assignment payloads and a dedicated assignment view in the requester chest screen.
6. Apply assignment eligibility before job claim and validate safe reassignment during transport.
7. Change both conversion costs to one redstone block.
8. Compile after each logical group, then run the complete acceptance matrix, including old-world migration, save/reload, two-player ownership, chest replacement, and cargo during reassignment.
9. Update version/reference docs and package the release only after tests pass.
